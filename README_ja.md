# llm-wiki-claude-skills (日本語版)

Markdownファイル、Wikiリンク（`[[Wikilink]]`）、およびファイルシステムアクセスを利用して、ローカル環境に個人用ナレッジWikiを構築・維持するための6つのClaudeエージェント用スキルです。

---

## 概要

本プロジェクトは、LLMエージェントがローカルファイルシステム上の構造化・相互リンクされたナレッジベースを段階的に構築・維持できるようにする、Claude用のインストール可能なスキル群です。
ユーザーがソースファイルを追加すると、エージェントがそれを読み込み、統合し、Wikiページに整理します。ユーザーが質問すると、エージェントはWikiを参照し、引用元を明示しながら回答します。Wikiは時間の経過とともに蓄積され、ソースのインプットや対話を経るほど、より豊かに成長していきます。

これは、後述の「LLM Wiki パターン」を個人的に実装したものであり、製品ではありません。バックエンドやAPI、クラウド同期（自身で導入しない限り）はなく、Claudeとファイルシステムへのアクセス以外に依存関係はありません。すべてローカルディスク上のMarkdownファイルで完結します。`.md` ファイルが読める環境であれば、Obsidian、Logseq、VS Code、iA Writer、または単なるフォルダとしてそのまま利用可能です。

Claude向けに作成されているため、パッケージ形式はClaude独自の `.skill` となっていますが、ベースとなるプロンプトはプレーンなMarkdownで書かれており、他のLLMモデル向けにも容易に移植できます（例えば、Codexの `AGENTS.md` などの仕組みに少しの書き換えで対応可能です）。

## 背景

（原著者による）

この実装は、私がObsidianを長年愛用し、LLMの可能性（と制限！）を学んできた経験から生まれました。最初はローカルのMarkdownファイルをダウンロードして使っていましたが、差分の管理や、ナレッジの新鮮さを維持するための管理作業（ブックキーピング）を面倒くさがってしまい、うまく続きませんでした。
しかし、ファイルシステムアクセスを可能にするMCP（Model Context Protocol）の登場で状況が一変しました。LLMエージェントが仲介者なしにディスク上のメモを直接読み書き・編集できるようになり、ブートストラップやノートの編集が劇的に高速化しました。それでもなお、数百もの半ば孤立したMarkdownファイル（と古いバージョン）の海に溺れないための規律を保つのは困難でした。

大きな転換点となったのは、[Andrej Karpathy氏のllm-wikiのGist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)でした。そこには、単発のRAG検索を行うのではなく、永続的で成長していくWikiをLLMに維持させるアプローチが記述されていました。「Wikiは、単に検索するためのドキュメントの山ではなく、ソースの読み込みや問い合わせのたびに豊かになる『コンパイルされた成果物（Compiled Artefact）』である」というKarpathy氏の洞察は、まさに求めていたものでした。

私が追加したのは、自分好みのワークフローに合わせるための、パッケージ化、設定方法、ソース追跡ルール、そして実際に運用する中で必要となったいくつかの設計上の選択肢のみです。

## 開発の過程で整理したアプローチ

| 観点 | Karpathy氏のコンセプト（オープン設計） | 本リポジトリの実装 |
| :--- | :--- | :--- |
| **生ソースの管理** | 変更不可の永続保存 | キュー（サブフォルダも再帰的に走査）。`ingested/` への移動をコミットとする（ファイルシステムが真実）。 |
| **処理状態の追跡** | `log.md` に処理済みの記録を残す | `ingested/` へのファイル存在自体を記録とする。`log.md` は監査用のみ。 |
| **対話の蓄積** | 「良い回答はWikiに書き戻す」（ヒントとして記載） | `/crystallize` コマンドを最優先機能化。対話や作業セッションをWikiに結晶化し、蓄積。 |
| **セッション起動時** | スキーマドキュメントの読み込み | Wikiのインデックスやドメインホーム（ハブ）ページが起動時のコンテキストとなる。 |
| **構成設定** | ディレクトリ構造の提案 | `wiki-config.md` に設定を一元化。全スキルがこれを参照。 |
| **ソースの属性** | 特に指定なし | フロントマターの `changes:` で `ingested/` 内のソースファイル名を紐づけて追跡。 |

中でも、`/crystallize`（結晶化）の導入は非常に強力でした。Karpathy氏が指摘するように、チャットで得た有益な回答は、履歴の彼方に消してしまうべきではありません。これは完全自動化されたアーカイブマシンを目指すものではなく、ユーザー自身が対話を通じて学習し、LLMが「散らかったMarkdownの整理役」となって、古い記述や矛盾、孤立したノートを見つけ出す共同作業です。長いブレインストーミングや作業セッションをWikiに「結晶化」させることで、次のセッションが開始された際の強力な共通コンテキスト（起動用ブートストラップ）として機能します。

## 6つのスキル

本プロジェクトは以下のスキルを提供します（※リポジトリにはREADME記載の5つに加え、振り分け用の `knowledge-router` が含まれています）。

| スキル名 | 機能 |
| :--- | :--- |
| **`wiki-ingest`** | `raw/` 内のファイルを処理してWikiページを生成・更新し、`ingested/` に分類して退避。 |
| **`wiki-query`** | Wikiのインデックスやページ群から回答を生成。Wikiリンクでの参照元を明示。有益な回答はWikiへ保存可能。 |
| **`wiki-lint`** | Wikiの健康状態チェック。リンク切れ、孤立ページ、インデックスの過不足を検証。 |
| **`wiki-integrate`** | 新規・更新されたページをインデックスや相互リンク（バックリンク）でナレッジグラフに繋ぐ。 |
| **`wiki-crystallize`** | チャットや作業内容を構造化されたWikiページ（または `overview.md`）に要約・結晶化する。 |
| **`knowledge-router`** | 会話内容を内省ノート（`my-knowledge`）と外部知識（`my-research`）に分類し、各インボックスへ振り分ける。 |

これらは個別にインストールして使うことも、組み合わせて使うことも可能です。最小限の構成であれば、`wiki-ingest` と `wiki-query` だけでも動作します。

## 必要条件

1. **ファイルシステムアクセス権を持つClaude**
   ローカルのファイルを読み書きするため、MCPサーバー（[Desktop Commander](https://github.com/wonderwhy-er/DesktopCommanderMCP) や [Anthropic公式のfilesystem MCP](https://github.com/modelcontextprotocol/servers/tree/main/src/filesystem) など）が必要です。
2. **Markdownで書かれたWiki用フォルダ**
   `[[wikilink]]` の形式に対応したMarkdownファイルのフォルダであれば、Obsidian以外のツールでも問題なく動作します。
3. **Claude Desktop（推奨）または Claude Code**
   Claude Desktop + MCPの組み合わせで動作確認を行っています。Web版やモバイル版ではローカルファイルへの直接書き込みができないため、制限があります。

## インストール手順

1. 本リポジトリから `.skill` ファイルをダウンロードします。
2. Claude Desktop を起動し、**Customize（設定） → Skills** を開きます。
3. 各 `.skill` ファイルをアップロード（インストール）します。

インストールすると、会話の中でスラッシュコマンド（`/wiki-ingest`、`/wiki-query`、`/wiki-lint`、`/wiki-integrate`、`/wiki-crystallize`、`/knowledge-router`）を使って直接呼び出せるようになります。何回か実行すると、エージェントが文脈に応じて自律的にこれらのスキルを提案するようになります。

## はじめに

### 1. 初期設定（任意）
スキル実行時に `wiki-config.md` が見つからない場合、自動的に作成プロセスが開始されます。
手動でセットアップしたい場合は、Wikiのルートフォルダに `wiki-config.md` を作成し、以下の内容を記述してください。**このファイルが置かれたフォルダが「Wikiのルート」として認識されます。**

```yaml
---
blacklist:
  - Repositories\
  - PrivateFolder\

index_excludes:
  - raw\
  - archive\
  - ingested\

ingested_folder: ingested

ingested_subdirs:
  - clippings
  - documentation
  - papers
  - articles
  - data
  - notes

log_format: "## [YYYY-MM-DD] {type} | {subject}"
---
```
*(※ `---` の下に、マニュアルや設定に関する解説テキストを記述することができます。)*

設定後、フォルダ構造は以下のようになります：

```text
your-wiki/
├── wiki-config.md
├── CLAUDE.md          ← エージェント向け運用ガイドライン
├── index.md           ← Wikiインデックス（エージェントが更新）
├── log.md             ← 監査ログ（エージェントが更新）
├── raw/               ← 未処理ファイルを置く場所
└── ingested/          ← 処理完了後の退避先
    ├── clippings/
    ├── documentation/
    ├── articles/
    └── notes/
```

### 2. `CLAUDE.md` の作成
エージェントに対し、Wikiの命名規則や重視すべきホーム（ハブ）ページなどを教えるためのルールファイルです。最初はシンプルな説明だけで構いません。エージェントが運用しながらこのドキュメントをブラッシュアップしていきます。

### 3. ソースを `raw/` に置いて実行
`raw/` フォルダにファイルを置き、Claudeで `/wiki-ingest` と入力するだけで、エージェントが内容を要約・反映し、インデックスを更新してファイルを退避させる一連のループが実行されます。

## プライバシーについて

本スキル自体には外部送信などのプログラムコードは含まれていません。しかし、**Wikiの内容はプライベート（完全非公開）ではありません。**
エージェントが読み書きするすべてのファイル（`raw/` 内の生データ、合成されたWiki、`CLAUDE.md`、インデックス）は、会話の文脈としてLLMプロバイダ（Anthropic等）のサーバーに送信されます。

そのため、以下の対策を推奨します。

```text
PCローカル環境
├── エージェントがアクセスできない領域（医療・財務・プライベート情報など）
└── ナレッジ管理領域（Obsidian Vaultなど）
    ├── Private/       ← 完全にアクセス不可にする（MCPの許可スコープから除外）
    └── Agent Access/  ← Wikiのルート（ここだけをMCPの許可スコープにする）
        ├── wiki-config.md
        ├── CLAUDE.md
        ├── raw/
        └── ingested/
```

- MCPサーバーの `allowedDirectories` 設定を、機密情報が含まれないWiki専用のルートフォルダ（例: `Agent Access` など）に限定してマウントしてください。
- `wiki-config.md` の `blacklist` はエージェントによる**書き込み**を防止するためのものであり、読み取りをブロックするものではありません。エージェントに見せたくないファイルは、MCPの対象フォルダ外に配置してください。
- 送信されたデータの取扱については、ご利用のLLMプロバイダのプライバシーポリシー（例: [anthropic.com/privacy](https://www.anthropic.com/privacy)）をご確認ください。
